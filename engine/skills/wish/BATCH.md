# Long batch

A batch that calls Codex sizes its worker pool from `AXIOM_CODEX_MAX_PARALLEL`, minus the slots the wish itself still needs, and never hard-codes a smaller pool.

have one fresh `chronos:dispatcher` run one pilot unit before any fan-out: a few items, in the foreground, its output checked, and whatever it shows fixed first. Only after a clean pilot does a dispatcher launch the full batch as a detached process in its own process group that outlives this session, removes any old completion marker when it starts, writes a progress file, and creates the marker only after all its work has succeeded; the dispatcher confirms the file advances and reports the two paths and the pid. Close the goal as `waiting` with a note naming the batch, and pass `progress_file` and `marker_file` as absolute paths and `pid` as the id of the process that lives until the batch ends, as the batch itself reports it (`$!` in Git Bash is not a Windows pid). No model runs while the goal waits: a headless `axiom wish` waits by itself, and in any other session tell the user to run `axiom wait <session>`. Axiom resumes this session when the marker appears or the process dies, and the message says which. A batch that died without its marker is a failure: diagnose it before anything else. Never watch a batch.
